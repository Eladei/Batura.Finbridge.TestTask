# Batura.Finbridge.TestTask
Тестовое задание для Finbridge на позицию Разработчик .NET

## Проекты, входящие в решение

| Проект | Описание |
|------------|------------|
| `Batura.Finbridge.TestTask.Api` | API-слой, содержащий контроллеры для доступа к данным |
| `Batura.Finbridge.TestTask.Api.Contracts` | API-контракты для взаимодействия API-слоя и пользовательского интерфейса |
| `Batura.Finbridge.TestTask.Application` | Слой приложения, содержащий команды и запросы для управления бизнес-операциями |
| `Batura.Finbridge.TestTask.Application.IntegrationTests` | Интеграционные тесты команд и запросов |
| `Batura.Finbridge.TestTask.Application.UnitTests` | Unit-тесты команд и запросов |
| `Batura.Finbridge.TestTask.Infrastructure` | Инфраструктурный слой. Содержит вспомогательные классы для реализации Outbox, шины событий на основе Kafka, контекст корреляции для логирования и т. д. |
| `Batura.Finbridge.TestTask.Model` | ORM-модель данных |
| `Batura.Finbridge.TestTask.UI` | Frontend-проект с пользовательским интерфейсом |

## Основные концепции

### Commands
- Команды выполняются при помощи `CommandExecutor`.
- Исполнитель команд осуществляет: контроль транзакции и логирование процесса выполнения команды. Тем самым он избавляет команды от необходимости дублирования данного функционала.
- В процессе выполнения команды могут сохранить события интеграции в Outbox в той же транзакции, что и результат выполнения бизнес-операций.
- В случае возникновения ошибок исполнитель команд откатит транзакцию.

### Queries
- Выполнение команд осуществляется через `QueryExecutor`.
- Исполнитель команд представляет собой удобную обертку, обеспечивающую единый процесс логирования запросов.

### Outbox
- В результате выполнения некоторых команд формируются события интеграции
- Чтобы гарантировать доставку события сохраняются в БД в той же транзакции, что и результаты выполнения команд
- Рассылка событий интеграции осуществляется фоновой job, расположенной в API-слое

### Принятые решения
- Команды представляют собой transaction script, т. к. текущее задание не содержит сложной предметной логики. Применение анемичной модели или DDD было бы избыточным.
- Как и команды запросы работают напрямую с моделью БД через Entity Framework.
- События интеграции не были вынесены в отдельный проект, т. к. микросервис один в рамках задания.
- Базовые классы команд и запросов, а также соответствующие исполнители операций не вынесены в отдельный проект и были размещены в Application-слое.
- CorrelationId не сохраняется вместе с событиями интеграции, т. к. задание не подразумевает чтение событий другим микросервисом.
- Каждый интеграционный тест выполняется в рамках индивидуальной БД для полной проверки интеграции.
- Топик users.topic для Kafka создается автоматически для простоты демонстрации работы. Однако данный подход следует избегать в production-среде.
- Для отслеживания всей цепочки операций задействован CorrelationId. Логи сохраняются в директорию logs (создается при отсутствии).
- Outbox реализован с учетом запуска нескольких экземпляров backend-микросервиса.
- На стороне БД реализована оптимистическая блокировка. В случае попытки конкурентного изменения данных будут приняты первые внесенные изменения, а другой пользователь получит ошибку.

## Развертывание системы
- Создайте БД на сервере PostgreSQL или разверните его в Docker-контейнере
- Накатите на БД миграцию из Batura.Finbridge.TestTask.Model
- В файле appsettings.Development.json проекта Batura.Finbridge.TestTask.Api скорректируйте: строку подключения к БД; настройки соединения с kafka. Другие параметры можно отрегулировать по желанию.
- В файле appsettings.Development.json проекта Batura.Finbridge.TestTask.UI прописана настройка для подключения к backend-сервису. Адрес указан аналогичный настройкам в launchSettings.json проекта Batura.Finbridge.TestTask.Api
- Для запуска интеграционных тестов добавьте .env-файл в проект Batura.Finbridge.TestTask.Application.IntegrationTests. Образец представлен в .envTemplate.txt
